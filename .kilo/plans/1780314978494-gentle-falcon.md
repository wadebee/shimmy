# Plan for Building a Google Cloud CLI Shim in Shimmy

## Objective
Create a shim for the Google Cloud CLI (gcloud) that allows users to run gcloud commands via Podman containers, following the conventions of existing shims in the shimmy repository.

## Steps

### 1. Create the Shim Script
- File: `shims/gcloud`
- Content: A POSIX shell script that:
  - Sets `set -eu` for error handling.
  - Determines the script directory and locates the shimmy-podman helper.
  - Defines configurable variables with defaults:
    - `SHIMMY_GCLOUD_IMAGE`: The container image to use (default: `docker.io/google/cloud-sdk:latest`)
    - `SHIMMY_GCLOUD_IMAGE_PULL`: Image pull policy (default: empty)
    - `SHIMMY_GCLOUD_CONFIG_DIR`: Path to gcloud config (set to `$HOME/.config/gcloud` if exists)
    - `SHIMMY_GCLOUD_KUBECONFIG`: Path to kubeconfig (set to `$HOME/.kube/config` if exists)
    - `SHIMMY_GCLOUD_PULL_ARG`: Pull argument based on policy
    - `SHIMMY_GCLOUD_TTY_ARG`: TTY argument if stdin and stdout are terminals
  - Sources the shimmy-podman helper.
  - Runs preflight checks for Podman.
  - Constructs the `podman run` command with:
    - `--rm` and platform flags
    - Pull and TTY arguments
    - Volume mounts for current directory (`$PWD:/work`) and working directory (`-w /work`)
    - Volume mounts for gcloud config (if set) and kubeconfig (if set) as read-only
    - Environment variable passthrough for `CLOUDSDK_*` (and optionally `GOOGLE_*`?)
    - The container image
    - Pass-through of command-line arguments (`"$@"`)

### 2. Create the Shim Configuration File
- File: `shims/gcloud.conf`
- Content:
  ```
  shim_config_version=1
  shim_name=gcloud
  smoke_arg=--version
  ```

### 3. Ensure Executable Permissions
- The shim script must be made executable (though in the repository we rely on the executable bit being set).

### 4. Follow Existing Conventions
- Mirror the structure of existing shims like `aws` and `terraform`.
- Use the shimmy-podman helper for common Podman operations.
- Allow overriding the image, pull policy, and other variables via environment variables.
- Mount the current directory to `/work` and set the working directory to `/work`.
- Pass through relevant environment variables (for gcloud, `CLOUDSDK_*`).
- Conditionally mount configuration directories if they exist in the user's home.

### 5. Considerations
- The gcloud SDK container image includes gcloud, kubectl, helm, and other tools. The shim will be named `gcloud` but the image can run other commands; however, the shim's purpose is to facilitate gcloud usage.
- We choose to mount the kubeconfig because the cloud-sdk includes kubectl and users may run `gcloud kubectl` or similar.
- We do not mount Docker config by default, as it is less commonly needed for gcloud alone.
- We pass through `CLOUDSDK_*` environment variables to allow users to configure the SDK.

### 6. Testing
- After creating the shim, users should be able to run:
  - `gcloud version` (or via the shimmy wrapper) to check the version.
  - `gcloud auth list` to see if credentials are picked up from the mounted config.
- The smoke test in the configuration file uses `--version`.

## Files to Create
- `shims/gcloud` (executable shell script)
- `shims/gcloud.conf`

## Dependencies
- Podman must be installed and running.
- The shim relies on `lib/shims/shimmy-podman.sh`.

## Notes
- We will not generate database schemas or migration SQL (as per the project's scope for database skills, but this is a shim).
- We will follow the naming conventions and code style from the repository.
